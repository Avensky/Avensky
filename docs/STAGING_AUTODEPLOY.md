# Rapid private staging updates

**Staging is a password-protected internal alpha, not a production release.** Every push or merge to `main` triggers GitHub Actions to build the frontend and deploy the matching Rust staging server when inputs have changed. The staging receiver accepts the catalog bundled by that build, switches the frontend symlink after the Rust health check, and does **not** require a new verified S3 manifest, root-side per-release approval, or an S3 download/ETag review.

**Private assets remain private.** The existing authenticated Caddy route serves `/__staging-assets/<release-id>/<logical-path>`. The gateway reads only asset URLs in a deployed staging bundle's catalog; it gets matching digest-keyed objects from private Lightsail S3 (with fallback to the existing storage layouts). Missing/unavailable models yield an asset 404/502, **not a blocked website deploy**. Existing manually verified releases and active sessions remain served. Commercial models are still not added to public GitHub or included in the frontend archive.

**One-time host update:** The existing staging SSH key is restricted to the old root-owned receiver, so GitHub cannot install its replacement. The script `deploy/staging-assets/bootstrap-auto-activate.sh` now installs the fast-path receiver and gateway **once**, backs up old binaries, configures gateway access to the existing staging releases directory, verifies that the original release still responds, and rolls back if the gateway doesn't recover. After that, future merges require no per-release terminal commands. The default staging root is `/srv/avensky-staging/frontend`; if installed elsewhere, pass its actual path as the third argument. Production is unchanged.

**What is still checked:** Vite build compilation, catalog path/hash shape, bundle-to-commit consistency, separate staging WebSocket health on a Rust update, and atomic previous-site rollback. Staging no longer requires full private S3 hash/ETag verification or a manual release-ID whitelist. Production retains explicit approval, staged-receipt checks, and its own release workflow.
