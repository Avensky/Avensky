# Staging tester access

The [alpha portal](../deploy/staging-access/portal.mjs) replaces the staging website's shared browser password dialog with individual tester access. It runs on Vultr at loopback port 9061 under its own account. Caddy asks the portal to authenticate both the staging site and its private model route. The Lightsail bucket, asset gateway on port 9060, and GitHub release connection keep their existing credentials. [Caddy forward-auth reference](https://caddyserver.com/docs/caddyfile/directives/forward_auth)

## Tester management

Sign in to the portal as the operator and open **Alpha testers**. Enter an approved tester's email and select **Send invite**. With a local mail relay configured, the portal delivers an invitation to that address. Without the relay, **Create invite** supplies a link to share with that tester. Each invitation is tied to one email, expires after three days, and can be used once. Select **Revoke access** to disable sign-in and invalidate the tester's browser sessions. **Grant access** enables a new sign-in. Only invite people covered by the asset terms.

Testers create a portal password and can add an authenticator under **Account**. The setup page supplies a key and confirms a six-digit code. Keep the one-use backup codes somewhere safe. The portal encrypts authenticator secrets with its server key. It stores password hashes, invitation digests, and session digests in its own SQLite database. [TOTP specification](https://www.rfc-editor.org/rfc/rfc6238)

Portal access and game characters have separate accounts in this iteration. A portal invitation authorizes the staging website and asset route. The game signs in separately and preserves existing character accounts and outfits. The game supports email and legacy account names.

## Install on Vultr

Use Node 24 on the staging host. Before editing Caddy, install the two portal modules in `/usr/local/lib/avensky/staging-access`, create the dedicated `avensky-alpha` Unix user and group, and install [the service unit](../deploy/staging-access/avensky-alpha-access.service). The unit creates `/var/lib/avensky-alpha` with private permissions.

Create root-owned `/etc/avensky/staging-alpha.env` at mode 0600. Set `AVENSKY_ALPHA_KEY` to the value generated by `openssl rand -hex 32`. Keep the key with the private database backup. For email delivery, point `AVENSKY_ALPHA_SENDMAIL` at the absolute path of a sendmail-compatible SMTP client usable by the service account, and set `AVENSKY_ALPHA_SENDER` to a verified sending address. A relay client can submit over SMTP without permission to write to a host mail spool. Leave the mail settings absent to create links for manual delivery.

Start the portal and confirm that a loopback request to `/__alpha/verify` returns 401 without a session. Create the first operator invitation on the server using the same environment.

```sh
systemd-run --wait --pipe --quiet --uid=avensky-alpha \
  -p EnvironmentFile=/etc/avensky/staging-alpha.env \
  --setenv=AVENSKY_ALPHA_STATE=/var/lib/avensky-alpha \
  /usr/bin/node /usr/local/lib/avensky/staging-access/portal.mjs invite-admin operator@example.net
```

Open that invitation privately. For an operator preview, expose only the new `/__alpha/*` route under the existing staging access guard. Test enrollment, login, two-factor setup, invitation delivery, and session revocation. Keep the existing release root and reverse proxies, then review [the Caddy handlers](../deploy/staging-access/staging.Caddyfile) before substituting the new guard on the staging site. Save the original Caddyfile and validate the candidate before reloading.

After cutover, verify that anonymous page requests go to the portal, anonymous range requests for models receive 401, and authorized requests receive the existing 206 response. Verify that an invite can be revoked before enrollment and that revoking a tester blocks the next asset read. Also test the staging phone login with an authenticator. The existing API domains are separate. The asset publisher's loopback health check still reaches 9060 directly.

If validation fails, restore the previous staging Caddyfile and reload it. Keep the portal database and key available for the next preview. Production has its own site and deployment path.
